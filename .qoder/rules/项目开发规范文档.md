# 项目开发规范文档（rules.md）

版本：v2.3（2026-06-27）
适用范围：本项目所有开发、测试、部署相关操作（含AI辅助开发）
核心原则：规范统一、环境隔离、可追溯、自动化落地、强制容器化部署、治本优先
架构特征：开发与生产位于独立的物理机器，通过 Git 同步代码，数据库完全隔离

---

> ⚠️ **【最高优先级警告】代码修改前必须检查分支！**
> 
> **任何代码修改操作前，AI 必须首先执行分支检查，禁止跳过！**
> 
> **强制执行步骤：**
> 1. 执行 `git branch --show-current` 获取当前分支名
> 2. 执行 `git status` 查看工作区状态
> 3. **【强制】输出判断结果**：明确说明当前分支是否为开发分支
> 
> **分支判断规则：**
> - 若返回 `main`：必须先切换到开发分支 `dev`，若不存在则创建，禁止在 main 上直接修改代码
> - 若返回 `dev`（或其他非 main 分支）：可直接继续在该分支上开发，无需创建新分支
> - **同时间只维护一个开发分支**，禁止为不同功能创建多个 feature/fix 分支

## 一、项目结构规范（必严格遵循）

项目根目录结构固定，禁止随意新增/删除一级目录，前后端目录命名、功能严格区分：

```plain text
你的项目/
├── .git               # 唯一Git仓库，禁止嵌套.git
├── .gitignore         # Git忽略规则，禁止修改prod相关忽略配置
├── dev/               # 开发环境（仅开发使用，提交至Git）
│   ├── frontend/      # 前端开发目录（如Vue/React项目）
│   └── backend/       # 后端开发目录（如Node/Java项目）
└── prod/              # 生产环境（仅服务器部署使用，不提交至Git）
    ├── frontend/      # 前端生产打包产物
    └── backend/       # 后端生产部署文件
```

- dev目录：仅存放开发阶段的代码、开发配置，所有开发操作均在dev下进行

- prod目录：仅在服务器本地存在，用于部署生产环境，禁止在本地dev环境操作prod目录

- 前后端目录：各自独立，前端仅在dev/frontend开发，后端仅在dev/backend开发，禁止跨目录写代码

## 二、Git分支规范（AI辅助执行，必遵循）

### 2.0 强制第一步（零容忍规则）

**判定触发条件（满足任一即触发）：**

| 触发条件 | 说明 |
|----------|------|
| 用户明确要求修改代码 | 如"修复"、"新增"、"重构"等 |
| 用户提出问题，AI 判断需修改 | 用户仅描述问题，AI 分析后判断需要代码变更 |
| AI 判断需要创建文件 | 任何 `create_file` 操作 |
| AI 判断需要修改文件 | 任何 `search_replace` 操作 |
| 任务包含"解释+修复" | 即使以"解释"开头，后续涉及代码变更 |

**强制执行步骤：**

1. **第一句话必须说**："我来检查当前分支状态"
2. **第一个操作必须是**：执行 `git branch --show-current` 和 `git status`
3. **【强制】输出判断结果**：
   - 明确说明当前分支名称
   - 明确说明本次修改的内容/功能
   - 判断当前是否在开发分支上：
     - 若在 `main` 分支：需切换到 `dev` 分支（不存在则创建），输出将切换/创建的分支名
     - 若已在开发分支（`dev` 或其他非 main 分支）：直接继续开发
4. **禁止跳过此步骤**：无论任务多么紧急，都必须先检查分支并输出判断

```
# 强制第一步命令（必须在任何代码修改前执行）
git branch --show-current   # 查看当前分支
git status                  # 查看工作区状态

# 【强制】输出判断结果示例

# 示例1：当前在 main 分支
当前分支：main
本次修改：修复退货凭证上传预览问题
判断结果：不适用（当前在 main 分支，禁止直接修改代码）
操作：切换到 dev 分支，若不存在则创建（git checkout -b dev）

# 示例2：当前在开发分支
当前分支：dev
本次修改：修复退货凭证上传预览问题
判断结果：适用（当前在开发分支，可以继续开发）
```

**违规判定**：如果 AI 在没有执行分支检查的情况下直接使用 `create_file` 或 `search_replace` 工具，即视为违规。

**常见违规场景警示**：
- ❌ 用户说"解释问题并修复"，AI 仅解释后直接创建文件
- ❌ 用户说"这个报错怎么解决"，AI 分析后直接创建/修改代码
- ❌ AI 判断"只需添加类型声明"，直接创建 typings.d.ts
- ✅ 正确做法：无论任务描述如何，只要涉及代码变更，先检查分支

### 2.1 分支命名规范

本项目采用**单一开发分支**策略，同时间只维护一个开发分支，避免分支过多导致管理混乱：

- 主分支：main（唯一生产分支，仅用于合并、部署，禁止直接在main上开发/修改）

- 开发分支：dev（唯一开发分支，所有功能开发、bug修复均在 dev 分支上进行）

- **禁止创建多个 feature/fix 分支**：不再为每个功能或修复创建独立分支，统一在 dev 分支上开发

- 分支生命周期：`dev` 分支长期存在，合并入 main 后不清除，持续作为开发主线

- 历史分支清理：已合并或废弃的 feature/fix 分支应及时删除，保持分支列表整洁

**分支流转流程：**
```
main ──创建──> dev ──开发/修复──> dev ──代码审查通过──> 合并至 main
                       ↑                          |
                       └───── 合并后继续开发 ←─────┘
```

**【强制】代码提交前验证**

在执行 git commit 前，必须完成以下验证流程：

1. **AI 完成代码修改后**：应输出修改内容摘要，告知用户需要验证的功能点
2. **等待用户验证**：用户在实际环境中验证功能是否正常
3. **用户确认后**：AI 才能执行 git add 和 git commit
4. **禁止行为**：AI 未经用户确认直接提交代码

```
# 正确流程
AI 修改代码 → 输出修改说明 → 等待用户验证 → 用户确认 → AI 提交代码

# 错误流程（违规）
AI 修改代码 → AI 直接提交代码（跳过用户验证）
```


### 2.3 禁止操作

- 禁止直接在main分支写代码、提交修改

- 禁止合并未经过代码审查的代码到 main

- 禁止跳过自测直接合并代码

- 禁止为不同功能创建多个 feature/fix 开发分支（统一使用 dev 分支）

- 禁止在 dev 分支未合并到 main 的情况下，又创建新的开发分支

## 三、开发规范（前后端通用+各自补充）

### 3.1 通用开发规范

- 代码风格：统一代码格式（如前端ESLint、后端代码规范），AI开发时需自动遵循对应规范，避免格式混乱

- 注释规范：关键代码（如接口、核心逻辑、工具函数）必须加注释，清晰说明功能、参数、返回值，便于后期维护

- 文件命名：小写英文+连字符，禁止中文、大写、特殊字符，如frontend/src/components/login-form.vue、backend/src/utils/request.js

- 依赖管理：前后端依赖各自在对应目录的package.json（或对应配置文件）中管理，禁止跨目录引用依赖

- 自测要求：开发完成后，必须在dev环境自测（前端调后端本地接口），确认功能正常后再合并到main分支

### 3.2 前端开发规范（dev/frontend）

- 目录结构：按框架规范组织（如Vue：src/components、src/views、src/api、src/utils），禁止随意新增一级目录

- 接口调用：统一封装请求工具，接口地址、请求方式集中管理，禁止在组件内直接写接口地址

- 样式管理：统一使用一种样式方案（如Scoped CSS、Tailwind），禁止混用，避免样式冲突

- 打包规范：开发完成后，执行npm run build生成dist文件，仅用于prod部署，禁止提交dist至Git（.gitignore已配置）

### 3.3 后端开发规范（dev/backend）

- 目录结构：按业务模块组织（如src/controller、src/service、src/model、src/config），禁止随意新增一级目录

- 接口规范：统一接口返回格式（如{code: 200, message: "success", data: {}}），异常处理统一封装

- 配置管理：开发环境配置放在dev/backend/.env（或对应配置文件），禁止硬编码配置（如数据库地址、密钥）

- 日志管理：统一日志输出格式，日志文件放在dev/backend/logs，禁止提交日志至Git（.gitignore已配置）

## 四、问题解决方法论与开发设计原则（零容忍规则）

> ⚠️ **【零容忍规则】与分支检查同等强制！**
>
> AI 在**修改代码修复问题**或**开发新功能**前，必须先输出三步诊断结果，禁止跳过。
> 无论问题大小、无论修复还是开发，直接动手写代码而不先诊断根因，即视为违规。
>
> **核心原则：开发时预防根因，修复时消除根因。** 本方法论同时适用于 Bug 修复和新功能开发——开发阶段不解决 L2 根因，就是给未来埋 Bug。

### 4.1 三步诊断法

**任何问题修复或新功能开发前，必须完成以下三步，禁止跳过：**

**第一步：症状/需求描述 → 根因追问**

描述表面现象或需求后，必须追问至少一层"为什么"，直到定位到架构/设计层面的原因：

| 层次 | 问题类型 | 修复场景示例 | 开发场景示例 |
|------|---------|------------|------------|
| L0 表面症状 | 用户看到的现象 | "催收差异接口返回400错误" | "需要新增催收延期审批功能" |
| L1 直接原因 | 代码层面的触发点 | "控制器中 `detailIds` 没有转成 `detail_ids`" | "延期天数不能超过30天，需在接口层校验" |
| L2 根因 | 设计/架构层面的缺陷 | **"前后端没有统一的字段映射机制，每个 API 都手动转换"** | **"30天是业务规则，硬编码会导致后续变更困难，应提取为可配置常量"** |

- L1 是"哪里坏了/怎么做"，L2 是"为什么会坏/怎样才不会坏"
- 修复只停留在 L1 就是治标，开发不考虑 L2 就是在制造未来的 Bug
- **【强制】** 方案必须说明 L2 根因。修复时即使本次不涉及 L2 改造，也必须在注释中记录；开发时必须评估当前设计是否会引入反模式

**第二步：同类问题排查**

定位到根因后，必须检查同一根因是否在其他位置也存在：

```
排查清单：
- 同一张表是否被其他服务直接查询？（→ 数据访问层缺失的根因）
- 同一字段是否在其他 API 也做了手动映射？（→ 数据契约缺失的根因）
- 同一阈值是否在其他文件也硬编码了？（→ 常量管理缺失的根因）
- 同一代码模式是否在其他组件也重复了？（→ 共享模式缺失的根因）
```

- 排查结果必须记录：哪些位置存在同类问题、是否需要一并修复
- 若同类问题暂不修复，必须标注为已知问题，不能假装不存在

**第三步：修复方案定级**

根据根因的深度，将方案分为三个级别：

| 级别 | 说明 | 适用场景 | 要求 |
|------|------|---------|------|
| **A 级：症状修复** | 只修复当前报错的具体位置 | 紧急修复、线上阻断性问题 | 必须同时记录 L2 根因，标注为待改进 |
| **B 级：根因修复** | 修复导致问题的架构/设计缺陷 | 有时间做正确的事； | 同类问题一并修复，消除复发可能；开发时避免引入新的设计缺陷 |
| **C 级：体系预防** | 建立规范/机制防止同类问题再次出现 | 战略性改进； | 制定规范、提取共享模式、建立检查机制 |

- **修复时默认应追求 C 级**，除非是线上紧急阻断才降级为 A 级
- **开发时默认应追求 C 级**。如果开发新功能时发现需要复制已有代码稍作修改才能满足需求，这通常意味着应该做 C 级（提取共享模式）

### 4.2 本项目常见"治标"反模式

以下反模式在本项目中已反复出现。**在 Bug 修复时遇到必须识别根因；在开发新功能时遇到必须拒绝使用，改用"治本"方案。**

**反模式1：字段映射补丁**

```
❌ 治标：在控制器中添加字段映射（detailIds → detail_ids）
❌ 开发时：新接口直接在控制器里逐字段映射参数
根因：前后端没有统一的 DTO 映射机制，每个 API 手动转换
✅ 治本：建立 DTO Mapper 层，统一处理 snake_case ↔ camelCase 转换
```

识别信号：代码中出现 `req.body.xxx → params.yyy` 的逐字段赋值，或开发时想"先这样写，后面再统一处理"

**反模式2：魔法数字打补丁**

```
❌ 治标：在当前文件中修改阈值数字（如把7天改成5天）
❌ 开发时：新功能中直接写 `if (days >= 15)`
根因：业务规则以硬编码形式散落在多个文件中
✅ 治本：提取到统一常量文件，所有位置引用同一常量
```

识别信号：代码中出现 `>= 15`、`<= 30` 等无注释说明的数字字面量；开发时设计文档说"默认15天"就直接写成15

**反模式3：缓存失效补丁**

```
❌ 治标：在某个写操作后手动调用 cache.invalidate()
❌ 开发时：写操作后"别忘了"在 Service 里加一行清缓存的代码
根因：缓存和数据库没有统一的访问层，写操作分散在各服务中
✅ 治本：收敛到 Repository 层，写入时自动失效相关缓存
```

识别信号：修改数据后需要"记得"清缓存，遗漏则产生数据不一致；开发时写入了缓存相关逻辑但分散在各处

**反模式4：组件内数据转换**

```
❌ 治标：在组件中添加数据格式转换逻辑（如 task_no → taskNo）
❌ 开发时：前端拿到后端数据后，在组件里手动转字段名
根因：后端返回的数据格式与前端期望不一致，没有统一的数据适配层
✅ 治本：后端通过 DTO 返回正确格式，或前端通过统一的响应拦截器转换
```

识别信号：组件中出现 `data.xxx_name` → `item.xxxName` 的手动转换；开发时想"后端不改了，我前端兼容一下"

**反模式5：复制粘贴实现**

```
❌ 治标：复制已有组件/函数，稍作修改后使用
❌ 开发时："之前的催收 Modal 和退货 Modal 很像，复制过来改改"
根因：缺少通用的共享组件/工具函数/Hook
✅ 治本：提取通用基类/共享模式，差异部分通过配置或插槽实现
```

识别信号：多个文件有结构相同但参数不同的代码块；开发时觉得"复制一下比较快"

### 4.3 修复方案输出规范

**AI 辅助修复时，必须在修改代码前输出以下内容：**

```
1. 症状描述：[用户反馈的问题现象]
2. 直接原因（L1）：[代码层面哪里出了问题]
3. 根因（L2）：[架构/设计层面为什么会出现这个问题]
4. 同类问题排查：[同一根因在其他位置的表现，列出文件路径]
5. 修复方案级别：[A/B/C 级及理由]
6. 修复范围：[本次修复涉及的文件和改动说明]
```

**Bug 修复示例：**

```
1. 症状描述：催收差异处理接口返回400错误
2. 直接原因（L1）：ar-collection-mutation.controller.ts 中 req.body.detailIds
   未转换为 service 期望的 detail_ids
3. 根因（L2）：前后端没有统一的 DTO 映射机制，37个文件中有100+个手动转换函数，
   每次新增/修改 API 都可能遗漏字段映射
4. 同类问题排查：
   - ar-collection.ts (前端API层) handlerId/startDate 未转 snake_case
   - return-order.mutation.controller.ts 同样存在手动字段映射
   - oa-approval 相关控制器中也有类似问题
5. 修复方案级别：B 级（本次建立 DTO Mapper，避免后续再遗漏）
6. 修复范围：
   - 新增 ar-collection.mapper.ts 统一催收模块的字段映射
   - 修改控制器使用 mapper 替代手动映射
   - 前端 API 层使用统一的参数转换
```

---

**AI 辅助开发新功能时，必须在编码前输出以下内容：**

```
1. 需求描述：[本次开发的功能/需求]
2. 直接实现（L1）：[代码层面怎么实现]
3. 根因评估（L2）：[当前实现方案是否会引入反模式或设计缺陷？如何避免？]
4. 同类模式排查：[项目中是否已有类似功能？能否复用？]
5. 开发方案级别：[B/C 级及理由。开发不应出现 A 级]
6. 开发范围：[本次开发涉及的文件和改动说明]
```

**新功能开发示例：**

```
1. 需求描述：新增催收延期审批功能
2. 直接实现（L1）：
   - 后端新增延期申请接口，校验延期天数 ≤ 30
   - 前端新增延期申请 Modal，填写延期天数和原因
3. 根因评估（L2）：
   - 30天阈值若硬编码在接口层，后续业务规则变更需改代码 → 应提取为 AR_EXTENSION_MAX_DAYS 常量
   - 延期审批 Modal 与现有催收 Modal 结构高度相似 → 应复用 ActionFormModal 模式，而非复制粘贴
   - 审批操作后需更新任务状态 → 应走 Repository 层自动失效缓存，避免手动清缓存
4. 同类模式排查：
   - 已有催收任务 Modal 遵循 ActionFormModal 模式 → 复用
   - constants.ts 已定义 AR_EXTENSION_MAX_DAYS → 复用
   - ar-collection.repository.ts 已有写入自动失效缓存机制 → 复用
5. 开发方案级别：B 级（复用已有模式，不引入新的设计缺陷）
6. 开发范围：
   - 新增 POST /api/ar-collection/:id/extend 接口
   - 复用 ActionFormModal 新增 ExtendModal 组件（≤150行）
   - 使用 AR_EXTENSION_MAX_DAYS 常量进行校验
```

### 4.4 A 级修复的根因追踪要求

当修复级别为 A（症状修复）时，必须：

1. **在代码注释中标注根因**：
   ```typescript
   // TODO: [根因] 前后端缺少统一 DTO 映射机制，此为临时字段转换
   // 待建立 DTO Mapper 层后统一处理
   const detailIds = req.body.detailIds;
   ```

2. **在提交信息中标注**：
   ```
   fix: 修复催收差异接口字段映射错误 (A级-根因:缺乏统一DTO映射机制)
   ```

3. **后续跟踪**：A 级修复不应长期存在，应在后续迭代中升级为 B 级

### 4.5 禁止的操作

- ❌ 发现 bug 后直接修改出错的那行代码，不追问根因
- ❌ 修复一处问题，不检查同一根因是否在其他位置也存在
- ❌ A 级修复不标注根因，导致后续无追踪、不改进
- ❌ 将"业务规则变更"误判为"bug 修复"——业务规则变更应评估是否需要将硬编码改为可配置
- ❌ 修复后不思考是否需要建立规范/机制来防止同类问题复发
- ❌ **开发新功能时遇到重复模式，直接复制粘贴已有代码，不提取共享组件/Hook/工具函数**
- ❌ **开发时遇到业务阈值/规则，直接硬编码在代码中，不提取为常量或可配置项**
- ❌ **开发接口时不使用 DTO Mapper，而是逐字段手动映射参数**
- ❌ **开发写操作时不在 Repository 层统一处理缓存失效，而是"写完记得清缓存"**

### 4.6 规范维护要求（强制遵循）

规范是活文档，必须随代码演进而同步更新。过时的规范比没有规范更危险——它会误导而非指导。

**触发规范更新的场景：**

| 触发场景 | 需要做的 | 示例 |
|---------|---------|------|
| 新增架构/设计模式 | 新增规范条目或新建规范文件 | 引入 Repository 模式 → 新增 `data-access-cache.md` |
| 修改已有模式的实现方式 | 更新对应规范条目 | DTO Mapper 从手动改为自动转换 → 更新 `data-contract-dto-mapping.md` |
| 发现规范未覆盖的反模式 | 在方法论中新增反模式 + 在架构规范中新增治本方案 | 发现新的"治标"模式 → 更新4.2反模式清单 |
| 项目技术栈变更 | 更新所有受影响的规范 | 切换ORM → 更新数据访问规范、数据契约规范 |
| 规范与实际代码不一致 | 以代码为准更新规范（除非代码本身是 bug） | 规范说"禁止any"但某处用了any → 修复代码或调整规范 |

**AI 的规范维护职责：**

1. **开发时主动检查**：AI 在修改代码时，应检查本次修改是否涉及现有规范，若涉及则提示用户是否需要同步更新规范
2. **C 级修复必须更新规范**：当修复级别为 C（体系预防）时，规范更新是修复的必要组成部分，不能只改代码不改规范
3. **新规范提案**：当发现反复出现的问题模式但现有规范未覆盖时，AI 应主动提出新增规范的建议，而非等用户要求

**规范维护的禁止操作：**

- ❌ 修改了代码架构但不更新对应规范，导致规范与代码脱节
- ❌ 发现规范过时但不更新，让过时规范继续"指导"后续开发
- ❌ 新建了规范文件但后续代码变更不再维护，规范变为僵尸文档
- ❌ 只在规范中写"禁止xxx"但不提供正确的替代方案（规范必须有"应该怎么做"而不仅是"不能怎么做"）

**规范版本管理：**

- 每次规范变更应在文件头部更新版本号和变更日期
- 重大变更（新增/删除规范条目）应递增主版本号（如 v1.0 → v2.0）
- 补充性变更（新增示例、澄清表述）递增次版本号（如 v1.0 → v1.1）

## 八、部署规范

### 8.1 环境隔离

- 开发环境和生产环境位于**不同的物理机器**，完全隔离
- 开发机（macOS）：本地开发、自测，使用独立的开发数据库
- 生产服务器（8.130.26.73）：Docker 容器化部署，使用独立的生产数据库
- 代码通过 Git 同步：开发机 push → 生产服务器 pull
- 禁止在生产服务器上直接修改代码，所有改动必须在开发机完成后通过 Git 同步
- 生产服务器的 `prod/` 目录和 `.env` 文件仅在该服务器上存在，不提交到 Git

### 8.2 强制容器化部署

> ⚠️ **【强制】本项目必须使用 Docker 容器部署，禁止直接运行进程！**

**禁止行为：**
- ❌ 直接运行 `node dist/app.js` 启动后端
- ❌ 直接运行 `nginx` 或 `nginx -s reload` 启动前端
- ❌ 使用 `nohup`、`pm2` 等进程管理工具

**唯一允许的部署方式：** 使用 `docker-compose` 容器化部署，且**必须通过 `deploy/scripts/deploy.sh` 脚本执行**。

### 8.2.1 部署脚本强制使用

> ⚠️ **【强制】禁止绕过 `deploy.sh` 脚本直接执行 `docker-compose` 命令！**

**必须行为：**
- ✅ 部署前检查 `deploy/scripts/deploy.sh` 是否存在
- ✅ 使用 `./deploy.sh` 执行完整部署流程（脚本自动检测 Dockerfile/package.json 变更，自动决定缓存策略）
- ✅ 使用 `./deploy.sh --skip-build` 执行仅重启容器（未修改代码时使用）

**禁止行为：**
- ❌ 直接执行 `docker-compose build`（即使加了 `--no-cache`）
- ❌ 直接执行 `docker-compose up -d`
- ❌ 直接执行 `docker-compose down`
- ❌ 以"脚本步骤我都懂"为由绕过脚本手动执行

**例外情况：**
仅当 `deploy/scripts/deploy.sh` 文件不存在时，才允许手动执行 `docker-compose` 命令，且必须在操作前向用户说明脚本缺失的情况。

### 8.3 单人开发工作流

本项目的标准开发流程（CI/CD 自动部署）：

```
dev 分支开发 → commit 存档（可多次）→ 自测 → git diff Review → 合并到 main → push main → 自动部署
```

| 步骤 | 操作 | 说明 |
|------|------|------|
| ① 写代码 | 在 dev 分支上开发 | 本地 :3100 + :8100 |
| ② commit | `git add . && git commit` | 可多次 commit 存档，不影响线上 |
| ③ 自测 | 本地跑起来验证 | 确认功能正常 |
| ④ Review | `git diff` 检查改动 | 检查多改/少改/遗留 |
| ⑤ 合并 | `git checkout main && git merge dev` | dev 合入 main |
| ⑥ push | `git push origin main` | 触发 GitHub Actions 自动部署 |

**自动部署流程**（GitHub Actions）：push main 后自动执行：
1. SSH 到生产服务器（8.130.26.73）
2. `git pull` 拉取最新代码
3. `deploy.sh` 构建 + Docker 打包 + 启动容器
4. 健康检查确认部署成功

工作流配置文件：`.github/workflows/deploy.yml`

### 8.4 部署流程（在生产服务器上执行）

**前置条件：** 生产服务器已通过 `git pull` 拉取最新代码。

#### 场景一：完整部署（代码已更新，需要重新构建）

**【强制】必须使用部署脚本**

```bash
ssh root@8.130.26.73
cd /www2/DevHub/supply-chain-dashboard
git pull
cd deploy/scripts
./deploy.sh
```

**脚本自动检测 Dockerfile/package.json 是否变更**：

| 场景 | 检测结果 | 行为 | 耗时 |
|------|---------|------|------|
| 仅代码更新 | Dockerfile/package.json 未变 | 复用缓存，仅更新 dist 层 | ~5 秒 |
| Dockerfile/package.json 变更 | 检测到变更 | 自动加 `--no-cache`，全量重构建 | ~3-4 分钟 |
| 首次部署 | 缓存 key 不存在 | 自动启用 `--no-cache` | ~3-4 分钟 |

脚本会自动完成以下步骤：
1. 源码-产物新鲜度预检（比较 `dev/*/src` 与 `prod/*/dist` 修改时间）
2. 前后端并行执行 `npm ci`（仅 package.json 变更时）+ `npm run build`
3. 原子性产物替换（构建失败自动回滚原始产物）
4. 构建产物摘要输出（大小、文件数）
5. `docker-compose build`（自动检测决定是否加 `--no-cache`）
6. `docker-compose up -d`
7. 执行健康检查

**脚本不可用时的手动执行（不推荐，仅限脚本缺失时）：**

```bash
# 步骤1：宿主机重新构建前后端产物
cd dev/frontend && npm install && npm run build
cd dev/backend && npm install && npm run build

# 步骤2：Docker 重新打包
cd deploy
docker-compose build
docker-compose up -d
```

#### 场景二：仅重启容器（未修改代码，仅重启服务）

```bash
cd deploy/scripts
./deploy.sh --skip-build
```

> ⚠️ `--skip-build` **仅适用于未修改代码的场景**。若已合并新代码但未重新执行宿主机 `npm run build`，`--skip-build` 会直接将旧的 `prod/*` 产物打包进镜像，导致部署旧版本代码。

#### 步骤三：验证服务状态

```bash
# 检查容器运行状态
docker ps

# 检查后端健康
curl http://localhost:8000/api/health

# 检查前端响应
curl -I http://localhost:3000
```

### 8.4 构建产物说明

#### 预构建产物模式

本项目 Dockerfile 采用**预构建产物打包**模式：

- Dockerfile **不编译源码**，仅将 `prod/*` 目录中的预构建产物复制到镜像内
- **部署前必须在宿主机执行构建**，更新 `prod/` 目录产物

> ⚠️ **关键提醒**：`prod/` 目录中的产物与当前分支源码是**独立维护**的。合并 dev → main 后，务必重新执行宿主机 `npm run build`，否则 `prod/` 中仍保留旧分支的产物。
>
> 部署前快速验证产物是否属于当前代码：
> ```bash
> ls -la prod/backend/dist/app.js prod/frontend/dist/index.html
> ```

### 8.6 部署脚本说明

项目提供标准化部署脚本：

| 脚本 | 路径 | 用途 |
|------|------|------|
| deploy.sh | `deploy/scripts/deploy.sh` | 主部署脚本 |

**deploy.sh 核心特性：**

| 特性 | 说明 |
|------|------|
| 并行构建 | 前后端 `npm ci && npm run build` 并行执行，缩短部署时间 |

| 参数 | 说明 | 适用场景 |
|------|------|---------|
| （无参数） | 宿主机构建 + Docker 构建（脚本自动检测缓存策略） | **所有部署** |
| `--skip-build` | 跳过宿主机构建和 Docker 构建，仅重启容器 | 未修改代码，仅重启服务 |
| `--backup` | 部署前创建 `prod/` 产物的备份 | 配合上述任意参数使用 |

> 💡 **无需手动干预缓存策略**，脚本自动检测 Dockerfile/package.json 变更，自动决定是否加 `--no-cache`。

### 8.9 更新日志维护（强制步骤）

> ⚠️ **每次部署后，AI 必须执行此步骤，不可跳过。**

**执行时机**：`deploy.sh` 执行完成、健康检查通过后

**流程：**

1. AI 根据本次开发内容，总结变更条目（版本号 + 类型 + 描述）
2. 向用户确认变更描述是否准确
3. 用户确认后，将新条目写入服务器上的 changelog.json：
   - 宿主机路径：`/data/changelog/changelog.json`
   - 容器内路径：`/app/data/changelog.json`（通过 volume 挂载同步）
4. 无需重启服务，刷新页面即可看到更新

> 首次部署后需手动将种子数据复制到服务器：
> ```bash
> cp dev/backend/data/changelog.json /data/changelog/changelog.json
> ```

**版本号规则：**

- 新增功能（feature）：minor 版本号 +1（如 v2.3.0 → v2.4.0）
- 修复/优化（fix/optimization）：patch 版本号 +1（如 v2.3.0 → v2.3.1）
- 重大架构变更（breaking）：major 版本号 +1

**变更类型定义：**

| 类型编码 | 中文标签 | 颜色 | 说明 |
|----------|----------|------|------|
| feature | 新功能 | green | 新增的业务功能或系统功能 |
| fix | 修复 | orange | 修复已知缺陷或错误 |
| optimization | 优化 | blue | 性能优化、体验优化、代码重构 |
| breaking | 重要变更 | red | 不兼容变更、数据库迁移、架构调整 |

**描述编写规范：**

- 使用中文，面向业务人员阅读
- 每条变更一句话描述，20-50字
- 说明“做了什么”而非“怎么做的”
- 避免技术术语（如 SQL、API、组件名等）
- ✅ 正确示例：“新增采购退货批量审核功能”
- ❌ 错误示例：“在 ProcurementReturn 模块添加了 batchReview API”

**JSON 格式要求：**

- `entries` 数组按日期降序排列（最新版本在前）
- 每个 entry 包含 `version`、`date`、`types`、`changes` 四个字段
- `date` 使用 `YYYY-MM-DD HH:mm` 格式，**时间必须取自 git 提交时间**（`git log -1 --format='%ai'`），不可手动估算或使用系统时间
- `types` 为数组，一个版本可包含多种变更类型

### 9.7 E2E 数据安全规范（共享数据库场景）

> ⚠️ **本项目开发和生产共用同一个数据库**，E2E 测试中的写操作会直接影响生产数据。已发生过 E2E 测试对真实 OA 审批实例执行“同意”操作导致生产数据被污染的事故。

#### 核心原则：谁创建，谁操作，谁清理

1. **E2E 测试只能修改自己创建的测试数据**，禁止修改数据库中已有的业务数据
2. **测试数据标记**：通过 API 创建的测试数据必须包含可识别标记（如标题含 `[E2E-TEST]` 前缀）
3. **强制清理**：每个写操作测试必须在 `afterEach` 中清理创建的测试数据，即使测试失败也要清理
4. **清理容错**：清理操作使用 try-catch 包裹，清理失败时输出警告但不阻断测试报告

#### E2E 测试安全分级

| 安全级别 | 操作类型 | 要求 |
|---------|---------|------|
| ✅ 安全 | 页面加载、导航跳转、元素渲染检查 | 无限制 |
| ✅ 安全 | 读取 API（GET 请求） | 无限制 |
| ⚠️ 受限 | 写入操作（POST/PUT/DELETE） | 只能操作自己创建的测试数据，且必须在 afterEach 中清理 |
| ❌ 禁止 | 修改系统配置、用户角色、权限分配 | 下沉到接口测试层（mock DB） |

#### 标准模板（创建 → 操作 → 清理）

```typescript
test.describe('审批操作测试', () => {
  let testInstanceId: number | null = null;

  test.beforeEach(async ({ apiClient }) => {
    const result = await apiClient.post('/api/oa-approval/instances', {
      formTypeCode: 'other_payment',
      title: '[E2E-TEST] 测试付款申请',
      formData: { /* ... */ },
    });
    testInstanceId = result.data?.id ?? result.id;
  });

  test.afterEach(async ({ apiClient }) => {
    if (testInstanceId) {
      try {
        await apiClient.delete(`/api/oa-approval/instances/${testInstanceId}`);
      } catch (e) {
        console.warn(`[E2E Cleanup] 清理失败: instanceId=${testInstanceId}`, e);
      }
      testInstanceId = null;
    }
  });

  test('同意操作更新审批状态', async ({ authenticatedPage }) => {
    await authenticatedPage.goto(`/oa/detail/${testInstanceId}`);
    // ... 执行审批操作 ...
```

### 9.13 AI 辅助编写测试规范

- **【强制】先运行再编写**：AI 编写测试前必须先运行 `npm test` 确认现有测试全部通过
- **【强制】验证通过**：AI 编写完测试文件后必须运行该测试文件确认全部通过
- **【强制】不使用 any**：测试代码中的 mock 对象也必须类型安全，使用 `jest.MockedFunction<typeof fn>` 或 `vi.MockedFunction<typeof fn>`
- **【强制】代码变更必须有测试伴随**：AI 新增或修改业务函数时，必须同步创建或更新对应的 spec 文件。新增模块不允许“先上线后补测试”
- **【强制】测试审查清单**：代码审查时必须逐项检查：
  - [ ] 新增/修改的业务代码是否有对应测试
  - [ ] 测试是否覆盖正常路径 + 边界值 + 异常路径
  - [ ] describe/it 描述是否清晰可定位
  - [ ] 是否复用 `__tests__/helpers/` 或 `e2e/helpers/` 工厂方法
  - [ ] spec 文件是否在 300 行以内
  - [ ] 是否使用 `any` 类型
  - [ ] `beforeEach` 是否清理 mock 状态
- **优先级**：纯函数/工具函数 > 中间件/服务 > 控制器 > 组件 > E2E
- **单个 spec 文件 ≤ 300 行**：超出时按功能拆分为多个 describe 块或多个文件
- **复用辅助工具**：后端使用 `__tests__/helpers/` 中的工厂方法，前端 E2E 使用 `e2e/helpers/` 中的封装方法，禁止在每个 spec 中重复编写 mock 逻辑

#### 何时必须写测试

| 场景 | 测试类型 | 说明 |
|------|---------|------|
| 新增 Service 函数 | 单元测试 | 核心业务逻辑 |

- **【强制】测试先行**：AI 编写业务代码后必须同步编写对应测试，新增模块不允许“先上线后补测试”；修改已有模块时若无测试应顺手补充关键路径测试
